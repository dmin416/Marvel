## 3. What the 10,000-year algorithm actually changes

- **Make *reasoning* cheaper:** a future-developed architecture may use symbolic logic, compressed representations, sparse activation, highly selective attention, rapid incremental learning, domain-specific solvers and exact tool calls rather than brute-force computation for everything.
- **Separate stored knowledge from active thought:** much of the assistant's knowledge can live on disks/databases, retrieved when useful. Frequent facts/models should be cached in RAM; slow disk access and networking remain real bottlenecks.
- **Use traditional programs for exact work:** numerical linear algebra, finite-element modeling, chemistry packages, circuit tools, theorem provers, compilers and verified routines may do tasks more accurately than free-form AI guesses.
- **No arbitrary factor:** there is **no defensible measured 1,000×, million× or billion× maximum efficiency figure**. The minimum hardware for an equally capable future general intelligence is unknown. A human-level assistant on a single Pentium III is **not guaranteed**; that would require an additional, unusually strong story stipulation.
- **Training is a second challenge:** code for a brilliant architecture is not already a trained intelligence. Shadow must specify how the model's skills, knowledge structures and error checking are created, loaded, validated and maintained, without disclosing D's sealed memories wholesale.
- **Hardware cannot be finessed:** a brilliant digital mind still waits for slow sensors, network connections and numerical simulations. A reasoning assistant designing an experiment is different from a machine executing a multi-billion-element simulation of it.

**Best defensible Marvel-world interpretation:** the algorithm is radically more **sample-, memory- and compute-efficient** than real-world 2000-era AI. It makes high-level research conversation feasible on a **moderate NovaCorp server/cluster**, not automatically on every household computer. It need not be the mathematical optimum for all conceivable problems.

## 9. Ten-thousand-year algorithm hypothesis: minimum seed and self-improvement

**Status: P — speculative design framework, not deployed equipment or established history.** Assume Shadow knows the results of 10,000 additional years of algorithmic and software-engineering progress, *not* automatically 10,000-year-future semiconductors. This assumption changes how efficiently existing hardware can be used, without specifying a measurable universal efficiency multiplier.

### 9.1 Minimum code is not minimum complexity

- A **four-line random chatbot** can vary its responses but does not reason.
- A **small memory-based chatbot** can learn exact associations; it cannot infer general principles just by storing questions.
- A **short generator** can rearrange words into novel sentences; novelty is not comprehension.
- A **few-line improvement loop** can mutate candidates, test them and retain better ones. That is optimization of a defined target, **not automatically improvement of general intelligence**.
- A **five-line `FutureMind()` example** is only an interface to an unspecified substantial implementation; it does **not** imply that the actual system fits in five lines.
- For story planning, an initial *seed* might be **hundreds to thousands of carefully written lines**, using substantial operating-system, compiler, mathematical and database libraries; this range is a narrative hypothesis, not an established lower bound. A fuller trustworthy product would need more software, configuration, training state, test suites, instruments and operational staff.

**Potentially efficient architecture:** compact reasoning core; modular symbolic and statistical learning; sparse/incremental computation; persistent compressed knowledge; retrieval from disk; verified domain-specific solvers; software-generating tools; automated regression tests; and isolated evaluation. Program code, trained state, stored knowledge and external simulation tools count separately.

**Self-improvement loop:** propose a change → reproduce benchmark performance on held-out tasks → check safety/correctness/resource use → retain a validated change or revert → monitor drift. Improvements are not presumed monotonic, and a program that modifies its code is not automatically better at reasoning. No unrestricted access to company finances, external networks, research instruments or its own evaluation criteria.

### 9.2 Five scales and three outcome bands

**What is being compared:** a *self-contained device or facility* containing processors, RAM, storage, power delivery and cooling; remote computing is **not** silently counted. Phone/laptop/car/building are *physical size and power-budget analogies*, not claims that a year-2000 consumer phone could host the described future software.

**Bands:**
- **Average:** ordinary engineering and software for the chosen era, without a successful revolutionary general-AI architecture.
- **Realistic advanced (D-world):** a well-engineered, tested implementation of Shadow's exceptional algorithms, using attainable contemporary components and appropriate spending. "Realistic" means internally plausible *given the fictional breakthrough*, not independently verified real-world capability.
- **Ideal:** best-case 10,000-year **software** efficiency with expertly engineered hardware and extraordinarily effective compression/learning. This is a deliberately stronger **optional story premise**, not an established result or mathematical optimum.

| **Phone / handheld** | Pocket-size; battery-powered; low single-digit watts sustained; little room for heat rejection | Fixed commands, simple search, templates and tiny language tools; a 2000-era handheld is especially limited | If trained off-device *before installation*: unusually good offline dialogue, personal recall, tutoring and bounded specialist reasoning; retrieval and simulations heavily constrained | A compact, broadly capable personal reasoning companion **if** the seed/model fits its memory and can run economically; still bounded by battery, storage and slow complex simulations |

**Do not equate computation with intelligence:** A higher FLOPS rate means more operations on a chosen workload; it does not establish that a machine reasons better. Conversely, low-line-count source code can invoke huge hidden libraries or giant pretrained knowledge stores.

### 9.4 Throughput, memory and limits: how to measure each size honestly

For any on-page implementation, record **year, processor class, count, usable RAM, persistent storage, sustained electrical power, thermal limit, model/state size, training origin, tokens or decisions per second on a named task, latency, simultaneous users, tool access, simulation benchmark, failure rate and supervision**. Benchmark the same problem on different sizes before comparing them. **Never label a performance tier "1000× stronger" without specifying a task and measurement.**

- **Reasoning latency:** depends on sequential operations, memory access and software efficiency, not just peak FLOPS.
- **Working context:** limited by actual RAM and active representations; disks and retrieval add capacity at latency cost.
- **Scientific simulation:** numerical precision, memory bandwidth, mesh size, solver and elapsed time impose separate costs.
- **Autonomy:** reliable long tasks need error detection, permissions, recovery and audit logs even with remarkable intelligence.
- **Scientific advancement:** a fast mind cannot replace measurements, reagents, prototypes, industrial machining or time-consuming longitudinal studies.

### 10.4 What counts as computing power in a scene

Record separately: **(1)** local processor(s) and measured task throughput, **(2)** RAM and active context, **(3)** local storage and learned state, **(4)** battery and sustained thermals, **(5)** link bandwidth/availability when connected, **(6)** remote hardware, **(7)** software/algorithm version and test results, and **(8)** external instruments and authorizations.
